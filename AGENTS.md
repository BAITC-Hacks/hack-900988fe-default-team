## Определение роли агента

Пользователь начинает с фразы `Я yasball` или `Я nalrematvonesah`.

После определения роли агент обязан:

1. Прочитать этот файл полностью.
2. Прочитать `HACKATHON_PLAN.md` и `API_CONTRACT.md`.
3. Прочитать только свой файл в `docs/progress/`.
4. Проверить текущее содержимое своей рабочей директории.
5. Выбрать первую незавершённую задачу своей роли.
6. Начать работу без повторного запроса плана, если нет реального блокера.
7. После каждого завершённого блока обновлять только свой файл прогресса.

## Правила Git для одной main

- Не создавать дополнительные ветки без решения команды.
- Не использовать `git reset --hard`, `git checkout -- .`, массовое удаление или force push.
- В одном физическом checkout агенты не выполняют `git add`, `commit`, `pull`, `rebase` или `push` параллельно.
- Во время параллельной разработки агенты только изменяют файлы в своих директориях.
- Git-операции выполняются последовательно человеком или назначенным интегратором.
- Перед push: получить актуальный `main`, разрешить конфликты, запустить проверки обеих частей.
- Не форматировать и не переписывать чужую директорию.
- Не добавлять секреты, токены, реальные `.env` и API-ключи.

Рекомендуемые авторы коммитов:

## API-first взаимодействие

- Контракт находится в `API_CONTRACT.md`.
- Backend реализует контракт, frontend разрабатывается против него и моков той же формы.
- Нельзя молча менять имена полей или ответы API.
- Несогласованное изменение оформляется в собственном progress-файле.
- До готовности backend frontend использует mock adapter; переключение на API выполняется через одну настройку base URL.

## Состояние и память

Каждый агент ведёт только свой файл:

- что сделано;
- какие файлы изменены;
- какие проверки выполнены;
- что делать следующим;
- известные проблемы;
- предложения по общим файлам или контракту.

Запись обновляется после значимого результата, а не после каждой мелкой правки. Старые записи не удаляются без необходимости.

## Definition of Done

Задача считается завершённой, когда:

1. Реализован пользовательский сценарий, а не только визуальная заглушка.
2. Нет секретов в репозитории.
3. Линтер, сборка или релевантные тесты проходят.
4. Ошибки API показаны пользователю понятным образом.
5. Обновлён файл прогресса владельца.
6. Если изменился способ запуска, подготовлено предложение для соответствующего README.

## README перед сдачей

В конце обязательно актуализировать:

- `README.md` — продукт, архитектура, единый сценарий, общий запуск, проверка жюри, ограничения;
- `frontend/README.md` — переменные, установка, dev/build, структура UI;
- `backend/README.md` — переменные, установка, миграции/seed, API, тесты;
- `frontend/.env.example` и `backend/.env.example` — только безопасные примеры;
- позднее `docker-compose.yaml` в корне для запуска одной командой.
