# Backend HackAlem AI

Backend MVP на Node.js 22.13+; Swagger UI поставляется через npm-зависимость. SQLite предоставляется встроенным модулем Node.js. API использует JSON и префикс `/api`; маршруты согласованы с корневым `API_CONTRACT.md`.

## Запуск

```powershell
cd backend
npm ci
Copy-Item .env.example .env
npm run dev
```

Для обычного запуска используйте `npm start`. По умолчанию сервер слушает порт `3388`, frontend разрешён на `http://localhost:5173`.

Все настройки и безопасные примеры перечислены только в `.env.example`. Команды запуска загружают локальный `.env`, если он существует; переменные процесса имеют приоритет. Заполните ключ провайдера локально или передайте его через окружение процесса. Файл `.env` и реальные ключи не добавляйте в репозиторий. Без настроенного провайдера доступен fallback.

Для диагностики backend по умолчанию выводит JSON-логи запросов: метод, путь без query-параметров, HTTP-статус, длительность и `requestId`. Тела запросов, ключи и черновики в лог не попадают. Отключите логи через `REQUEST_LOGGING=false`.

## Docker

Соберите образ из корня репозитория:

```powershell
docker build -t hackalem-backend ./backend
```

Запустите backend с постоянным SQLite-том и безопасными настройками без LLM-ключа:

```powershell
docker run --rm -p 3388:3388 --name hackalem-backend -v hackalem-data:/app/data -e FRONTEND_ORIGIN=http://localhost:5173 hackalem-backend
```

После запуска API доступен по `http://localhost:3388/api`, Swagger — по `http://localhost:3388/api/docs`. Чтобы включить провайдера, передайте `LLM_API_KEY` через окружение команды запуска или файл окружения, который не добавляется в Git.

## Smoke-проверка

Матрица требований, демо-набор и ограничения: [готовность backend](docs/requirements.md). Полный автономный сценарий с временным сервером и проверкой перезапуска: `npm run test:acceptance` из backend. Тест не обращается к рабочей базе и не требует внешнего LLM.

После запуска сервера проверьте health, Swagger UI и OpenAPI-спецификацию:

```powershell
npm run smoke
```

Для другого API укажите базовый URL с префиксом `/api`:

```powershell
$env:SMOKE_BASE_URL = "https://haa-api.defaul7.net/api"
npm run smoke
```

## API и сценарий

Реализованы health check, анализ черновика, формирование карточки, создание/редактирование/публикация задачи, каталог с `theme`, `level`, `sort`, создание/просмотр откликов и ручное изменение статуса (`pending`, `selected`, `rejected`). Низкий рейтинг не мешает публикации; выбор команды не выполняется автоматически. Ошибки имеют контрактный вид `{ "error": { "code", "message", "details" } }`.

Валидация проверяет JSON-тела, подтверждённые поля, ответы AI-конструктора, статусы, параметры каталога и HTTP(S)-ссылку на прототип.

Публикация возвращает `409 UNCONFIRMED_TASK`, если нет ни одного допустимого подтверждённого поля с непустым текущим значением. Минимального рейтинга нет: даже score 0 допустим при подтверждённом названии. Пробелы не считаются заполненным значением.

В `PATCH /api/tasks/:taskId` передавайте `fields` и полный актуальный `confirmedFields`. Массив полностью заменяет прежние подтверждения; `[]` снимает все. Изменённое значение, явно включённое в этот список, считается повторно подтверждённым. Если список отсутствует, API возвращает `400`. Compose всегда возвращает score 0 до отдельного сохранения и подтверждения карточки.

JSON-тело должно быть объектом; `null`, массивы и скалярные значения возвращают `400 VALIDATION_ERROR`, повреждённый JSON — `400 INVALID_JSON`. Неподдерживаемые поля карточки и ответы с неверной парой questionId/field или повторным questionId тоже отклоняются. Максимальный размер тела — 1 МБ (`413 PAYLOAD_TOO_LARGE`).

### Темы и команды для frontend

Согласованное расширение реализовано и описано в Swagger. В POST и PATCH задачи можно передать верхнеуровневое поле `theme`: `operations`, `hr`, `finance`, `education`, `sustainability`. Например:

```json
{
  "theme": "finance",
  "fields": { "title": "Сводный отчёт расходов", "users": "Финансовые аналитики" },
  "confirmedFields": ["title", "users"]
}
```

При POST без темы ответ содержит `theme: null`; PATCH без темы сохраняет прежнее значение. Явно переданная тема должна входить в список (null и пустая строка отклоняются). GET задачи и каталог возвращают тему; фильтр — `GET /api/tasks?theme=finance`.

`GET /api/teams` возвращает массив профилей с полями `id`, `name`, `university`, `interests`, `skills`, `technologies`. Последние три поля — массивы строк. Выбранный `id` передаётся как `teamId` при создании отклика. Бизнес может вручную выбрать несколько команд.

После запуска Swagger UI доступен по адресу `http://localhost:3388/api/docs`, а исходная OpenAPI-спецификация — по `http://localhost:3388/api/openapi.json`.

Рейтинг детерминированный, диапазон 0–100. Баллы начисляются только за непустые поля, перечисленные в `confirmedFields`. AI вызывается через настраиваемый OpenAI-совместимый Chat Completions API с JSON Schema Structured Output (старый режим OpenAI Responses также сохранён); при отсутствии ключа, ошибке API или неверном ответе используются fallback-вопросы. Backend принимает AI-поле только когда его текст подтверждён исходным черновиком; неподтверждённые значения очищаются и заменяются уточняющими вопросами.

Backend отклоняет явные несоответствия категории по началу фрагмента: например, «Доступны данные…» в need или «Ожидаемый результат…» в data. Обязательных ключевых слов нет: «Прототип анализа данных», «Хотим сократить очереди» и контактный email сохраняются, если присутствуют в черновике. При сравнении игнорируются регистр и повторные пробелы, но сохраняется пунктуация адресов и чисел. Эвристика не гарантирует смысловую правильность любого фрагмента; распределение проверяется человеком перед подтверждением.

### Формула рейтинга

| Категория | Поля, которые должны быть заполнены и подтверждены | Баллы |
|---|---|---:|
| Контекст и потребность | context **и** need | 20 |
| Данные и материалы | data | 20 |
| Ожидаемый результат | expectedResult | 15 |
| Критерии успеха | successCriteria | 15 |
| Ограничения | constraints | 10 |
| Пользователи | users | 10 |
| Связь с бизнесом | contact **и** interactionFormat | 10 |

Если хотя бы одно необходимое поле пустое или не подтверждено, категория получает 0. `scoreBreakdown` сохраняет ключи `context` и `businessConnection` для составных категорий. `missingFields` результата рейтинга содержит ключи категорий без баллов; в анализе черновика это имена отсутствующих полей карточки. Рекомендации для редактора берутся из `scoreBreakdown[].recommendation`.

Уровни: 0–39 — draft, 40–69 — working, 70–89 — ready, 90–100 — priority. Каталог содержит все опубликованные задачи, включая низкий рейтинг; по умолчанию сортируется по убыванию баллов. После изменения формулы сохранённые задачи пересчитываются при запуске backend.

### Сценарий проверки жюри через Swagger

1. Выполните analyze с черновиком «Хотим сократить очереди в корпоративной столовой с помощью AI.». Получите минимум три вопроса; без провайдера допустим `fallbackUsed: true`.
2. Выполните compose с полученным analysisId и ответами на реальные пары questionId/field. Начальный score должен быть 0.
3. Создайте задачу с theme `operations`, fields из compose и полным списком вручную подтверждённых полей. Для роста до 100 заполните все поля формулы, подтвердив context вместе с need, contact вместе с interactionFormat.
4. Измените need через PATCH и исключите его из полного confirmedFields: рейтинг уменьшится на 20. Повторно подтвердите актуальное значение — 20 баллов вернутся.
5. Сохраните актуальные поля и подтверждения через PATCH **перед** publish. Publish работает с сохранённой версией; отсутствие любых непустых подтверждённых полей возвращает 409. Подтверждённый users со score 10 публикуется.
6. Проверьте GET /api/tasks с theme `operations`, level и sort `score_desc`: опубликованная задача видна при соответствующих фильтрах.
7. Возьмите id из GET /api/teams и отправьте отклик с идеей, планом, сроком и тестовой ссылкой на прототип. Создайте второй отклик от другой команды.
8. Получите список откликов и вручную установите selected обоим: выбор нескольких команд допустим. Проверьте также rejected и pending.

Эти API-сценарии покрыты `npm test` на временной SQLite и локальном тестовом провайдере. Браузерный прогон и реальный внешний LLM проверяются отдельно.

## Данные

Новый seed содержит пять разных задач и уместных откликов: столовая (30 баллов), адаптация сотрудников (50), сводка расходов (80), подбор заданий (90), энергопотребление (100). Все карточки опубликованы, все отклики изначально pending. Все десять полей присутствуют в карточках; пустые значения намеренно показывают пробелы. Старые записи не заменяются новым seed. Для демонстрации нового набора используйте отдельную пустую базу.

При неудачной записи SQLite backend возвращает 500 INTERNAL_ERROR и восстанавливает состояние памяти из последней сохранённой версии. Незавершённые AI-анализы хранятся только в памяти; карточки и отклики — в SQLite. Для одного файла базы запускайте один процесс backend.

Используется SQLite, путь к базе задаёт `DATABASE_URL` в формате `file:./dev.db`. При первом запуске создаются таблицы `tasks`, `teams`, `proposals` и пять синтетических задач, команд и откликов. Изменения задач и откликов сохраняются между перезапусками. Если нужен чистый demo seed, остановите сервер и удалите только файл `backend/dev.db`.

Профили команд содержат интересы, навыки и технологии. При старте существующая SQLite-база автоматически получает три JSON-колонки профиля; новые колонки известных demo-команд заполняются синтетическими значениями. Миграция сохраняет имена команд, задачи, отклики и последующие изменения профилей. Пересоздавать базу для этой миграции не нужно.

В `fixtures/drafts.json` находятся пять исходных черновиков разных отраслей, от минимального до полного. Для AI-прогона передайте значение `draft` выбранной записи в `/api/task-drafts/analyze`, а `theme` — при сохранении задачи. Отдельный HTTP endpoint для fixtures не вводился.

## Структура

- `src/server.js` — HTTP-маршруты, валидация и единый формат ошибок;
- `src/scoring.js` — детерминированный рейтинг;
- `src/ai.js` — Structured Output и fallback;
- `src/store.js` — SQLite, миграция профилей и demo seed;
- `src/task-schema.js` — единые списки полей карточки и тем;
- `src/demo-teams.js` — пять синтетических профилей команд;
- `fixtures/drafts.json` — пять исходных черновиков для демонстрации;
- `test/scoring.test.js` — тесты scoring service.

## Проверка ответов AI

В режиме Chat Completions читается `choices[0].message.content` только при `finish_reason: stop`, без отказа или вызова инструментов. REST-ответ Responses API читается из текстовых блоков сообщений assistant в массиве `output`, независимо от позиции сообщения. Принимается только завершённый ответ с ожидаемой структурой; отказ, неполный ответ, ошибка сети и некорректный JSON включают fallback.

Вопросы имеют уникальные поля и непустой текст. Сначала уточняются отсутствующие сведения; если их меньше трёх, добавляются вопросы для уточнения уже извлечённых сведений. Такое уточнение не подтверждает поле автоматически. `missingFields` содержит все отсутствующие поля анализа, а не только три поля вопросов.

Тесты провайдера используют подмену сети с реальным форматом REST-ответа и не требуют ключа или внешних запросов. Отдельный вызов настоящего OpenAI API остаётся интеграционной проверкой.

## Подключение провайдера

В шаблоне окружения указан OpenRouter и модель qwen/qwen3-coder-next; для локального vLLM замените адрес и идентификатор модели. Адреса записываются обычным текстом, без Markdown-ссылок. Для локального сервера без авторизации ключ можно оставить пустым.

Пустой базовый адрес явно отключает LLM. Если настройка базового адреса полностью отсутствует, работает прежняя конфигурация OpenAI Responses. При наличии адреса используется исключительно выбранный провайдер; автоматического перехода к другому провайдеру нет.

Для анализа можно задать отдельную модель; иначе используется общая. Настройки ролей чата и планирования пока зарезервированы и не используются. Температура, таймаут и дополнительные заголовки берутся из шаблона; таймаут распространяется на запрос и чтение ответа.

Провайдер должен поддерживать JSON Schema через `response_format`. [OpenRouter указывает, что поддержка зависит от endpoint провайдера](https://openrouter.ai/docs/guides/features/structured-outputs). При несовместимой модели или ошибке конфигурации возвращаются локальные fallback-вопросы. Это не подтверждает доступность конкретной модели: реальный вызов проверяется отдельно после настройки нового ключа.

## Публикация через домен

Backend по умолчанию слушает порт `3388`. Внешний API: `https://haa-api.defaul7.net/api`, frontend: `https://haa.defaul7.net`. Шаблон окружения настроен на эти домены. Для локального frontend настройте разрешённый origin по месту запуска.

Если Nginx работает на том же хосте, добавьте в существующий HTTPS server-блок домена API следующий location, сохранив текущие настройки TLS:

```nginx
location / {
    proxy_pass http://127.0.0.1:3388;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 75s;
}
```

Путь `/api` сохраняется. Если прокси находится в контейнере, вместо loopback используйте доступный из него адрес backend. Настройка домена в окружении сама по себе не меняет reverse proxy или DNS.
